## The story

Before a single line of Java exists, the repository itself has to be trustworthy: it must
contain the project and nothing else, ignore build junk and IDE files, and store every
text file with the same line endings no matter which operating system wrote it. You are
on Windows; everything this project runs on — Docker, Redis, Postgres init scripts,
GitHub Actions, Kubernetes — is Linux. A file that leaves your machine with Windows line
endings can break silently on the other side.

**Done looks like:** `main` exists on GitHub with the planning docs, a root `.gitignore`
and a root `.gitattributes`, and `git status` shows nothing that shouldn't be there.

## Ways to build it

| Option | How it works | Trade-off |
|---|---|---|
| Rely on `core.autocrlf` | each developer sets it in their own git config | personal, unenforceable; CI and teammates may differ |
| Editor settings (`.editorconfig`) | the editor writes LF | only covers files saved in that editor; git still converts |
| **Committed `.gitattributes`** | rules live in the repo and travel with every clone | one file to maintain — and it wins over personal settings |

## What we chose and why

A committed `.gitattributes` with `* text=auto eol=lf`, plus explicit LF for `*.sh`,
`*.lua` and `mvnw`, CRLF for `*.cmd`/`*.bat`, and `binary` for jars, images and PDFs.
It is a **project rule**, not a personal preference, so every clone and the CI runner get
the same bytes. `core.autocrlf` would win only for a solo developer who never shares
files with Linux — not our case.

The first commit went **straight to `main`**: an empty repository has no commit to branch
from, so there is nothing a pull request could compare against. This is the only direct
commit to `main`; every later ticket uses a branch and a PR.

## Under the hood

### .gitignore scope and precedence

- **What it is:** a list of path patterns git will not offer to track.
- **Behind the scenes:** git reads every `.gitignore` from the repo root down to the
  file's folder; a rule applies to its own folder and everything below it. Deeper files
  can override shallower ones (`!pattern` re-includes). There is also a **local-only**
  list in `.git/info/exclude` that is never committed — we used it for the presentation.
- **The trap you hit:** a `.gitignore` inside `src/main/java/com/stadium/inventory/`
  only covered that package, so `.idea/` and `target/` at the top still showed up.
- **Check:** `git check-ignore -v <path>` prints which file and line ignores a path.
- **Source:** [gitignore documentation](https://git-scm.com/docs/gitignore)

### Index vs working tree

- **What it is:** git keeps three copies of a file — the last commit, the **index**
  (what you staged) and the **working tree** (your disk).
- **Behind the scenes:** `git add` copies disk → index; `git commit` turns the index into
  a commit; checkout copies commit → disk. Each copy changes independently.
- **The trap you hit:** you staged a file, then deleted its folder. `git status` showed
  `AD` — *added* in the index, *deleted* on disk. `git rm --cached` removes it from the
  index only.
- **Source:** [Pro Git — Recording changes](https://git-scm.com/book/en/v2/Git-Basics-Recording-Changes-to-the-Repository)

### .gitattributes and line-ending normalisation

- **What it is:** per-path rules for how git treats a file (text or binary, line endings, diff).
- **Behind the scenes:** on `git add`, a `text` file is **normalised** to LF in the index;
  on checkout, `eol=` decides what lands on disk. `text=auto` lets git guess text vs
  binary from the content. `binary` = no conversion and no text diff.
- **Why it beats `core.autocrlf`:** attributes are committed and are checked **first**;
  `autocrlf` is a per-machine config nobody can enforce.
- **Why it matters here:** a shell script checked out with CRLF has a first line of
  `#!/bin/sh\r` → `bad interpreter: /bin/sh^M`. A Lua script with CRLF gets a different
  SHA1 in Redis (`EVALSHA` identifies scripts by their bytes) than the LF version CI loads.
- **Existing repos:** files committed before the attributes existed keep their endings
  until `git add --renormalize .`.
- **Source:** [gitattributes documentation](https://git-scm.com/docs/gitattributes) — section *End-of-line conversion*

### Upstream branches (`git push -u`)

- **What it is:** a link from a local branch to a remote one.
- **Behind the scenes:** `-u` writes `branch.main.remote` and `branch.main.merge` into
  `.git/config`, so plain `git push` / `git pull` know where to go and `git status` can
  report *ahead* / *behind*.
- **Source:** [git push documentation](https://git-scm.com/docs/git-push) — option `--set-upstream`
