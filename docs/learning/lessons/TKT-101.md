## The story

Five services will live in this repository. Before any of them does something useful, we
need the thinnest thing that runs **end to end**: one command at the repository root
builds every service and runs its tests, and the first service — `inventory` — starts and
answers "I'm healthy" over HTTP. That is a **walking skeleton**: no features, but every
joint moves.

It also fixes one decision for the whole project: the Spring Boot version is written
**once**, at the root, and every service inherits it. Five services can then never drift
onto five different Boot versions.

**Done looks like** (the ticket's acceptance criteria):
- `./mvnw clean verify` **from the root** builds `inventory` and runs its tests — green.
- `inventory` started locally answers `GET http://localhost:8081/actuator/health` → 200, `UP`.
- `services/inventory/pom.xml` declares no version for any Boot-managed dependency.
- One Maven Wrapper, at the root.
- The **Commands** section of `CLAUDE.md` is filled in.

## Ways to build it

| Option | How it works | When it wins |
|---|---|---|
| One repo + one build per service | each service is a standalone Maven project with its own wrapper | truly independent teams and release cycles |
| **Root POM = aggregator + parent** | the root lists the modules (`<modules>`) *and* is every module's `<parent>`; the root's parent is `spring-boot-starter-parent` | one team, one Boot version, one command builds everything |
| Root = aggregator only, versions via a BOM | the root only lists modules; each service imports `spring-boot-dependencies` in `<dependencyManagement>` | a company already forces its own parent POM on every project |

## What we chose and why

**Root POM as both aggregator and parent**, with `spring-boot-starter-parent` 4.1.x as
*its* parent. One file holds the Boot version and Java 21; `./mvnw verify` at the root
builds every module in the right order (Maven's *reactor*). The BOM-only option is just
as valid but adds a `<dependencyManagement>` import and loses the plugin configuration
the starter parent gives for free (compiler release, `spring-boot-maven-plugin`
defaults, resource filtering). We have no corporate parent to fight, so we take the
simpler path.

Dependencies arrive **just in time**: this ticket uses only **Spring Web** and **Spring
Boot Actuator**. Postgres, Redis and Testcontainers come with the tickets that need them.

## Under the hood

### Aggregator vs parent POM

- **Aggregator** (`<packaging>pom</packaging>` + `<modules>`): tells Maven *what to build*.
  Running a command on it runs the same command on every listed module, ordered by their
  dependencies (the **reactor**).
- **Parent** (`<parent>` in the child): tells a module *what to inherit* — properties,
  `<dependencyManagement>`, `<pluginManagement>`, plugin configuration.
- The two are independent; our root plays both roles. The child finds its parent through
  `<relativePath>`: **empty** (`<relativePath/>`, what Initializr generates) means "skip
  the file system, look in the repository" — so it would ignore our root POM. It must
  point to the root POM file.
- **How versions flow:** `spring-boot-starter-parent` → `spring-boot-dependencies`, a huge
  `<dependencyManagement>` list of tested versions. Children declare a dependency
  *without* a version and get the managed one. Declaring a version yourself overrides it
  — that is what the acceptance criterion forbids.
- **Source:** [Maven — Introduction to the POM](https://maven.apache.org/guides/introduction/introduction-to-the-pom.html) — sections *Project Inheritance* and *Project Aggregation*

### Starters and auto-configuration

- **A starter** is a dependency with no code of its own, just a curated set of
  dependencies. *Spring Web* = `spring-boot-starter-webmvc` (Spring MVC, Jackson, embedded
  Tomcat).
- **`@SpringBootApplication`** = `@SpringBootConfiguration` (this class is configuration) +
  `@ComponentScan` (find your `@Component`s from this package down) +
  `@EnableAutoConfiguration` (load Boot's auto-configuration classes).
- **Auto-configuration** classes are listed in `META-INF/spring/…AutoConfiguration.imports`
  inside each Boot jar and guarded by conditions: `@ConditionalOnClass` (only if Tomcat is
  on the classpath), `@ConditionalOnMissingBean` (only if *you* didn't define one),
  `@ConditionalOnProperty`. Adding a starter → its classes appear → its conditions pass →
  beans exist. That is the whole "magic".
- **Boot 4 difference:** auto-configuration is split into **one module per technology**.
  Use the starter, not the raw library — a raw library on the classpath may no longer
  switch anything on (ADR-0004 table). `spring-boot-starter-web` is now
  `spring-boot-starter-webmvc`.
- **See it yourself:** start with `--debug` and read the *Conditions Evaluation Report*.
- **Source:** [Spring Boot reference — Auto-configuration](https://docs.spring.io/spring-boot/reference/using/auto-configuration.html)

### Actuator's health endpoint

- Adding **Spring Boot Actuator** registers endpoints; only **`health`** is exposed over
  HTTP by default, at `/actuator/health`.
- The response status follows the aggregated health: `UP` → **200**, `DOWN` /
  `OUT_OF_SERVICE` → **503**. That is what load balancers and Kubernetes probes read.
- `management.endpoint.health.show-details` defaults to **`never`** — you see the overall
  status, not the components (`db`, `redis`). TKT-103 will deliberately change that for
  local runs and tests only.
- **Source:** [Spring Boot reference — Actuator endpoints](https://docs.spring.io/spring-boot/reference/actuator/endpoints.html)

### Testing a running server in Boot 4

- `@SpringBootTest(webEnvironment = RANDOM_PORT)` starts the **real** embedded Tomcat on a
  free port — your test talks HTTP to it, exactly like a client would.
- **`RestTestClient`** (new in Spring Framework 7 / Boot 4) is the client for that; add
  `@AutoConfigureRestTestClient` to the test class and inject it. It already points at
  the random port and has a fluent API for asserting status and JSON. Initializr's test
  dependency for Spring Web (`spring-boot-starter-webmvc-test`) already brings it in.
- **Boot 4 differences:** `@SpringBootTest` no longer sets up MockMvc on its own (you'd need
  `@AutoConfigureMockMvc`); `TestRestTemplate` moved to a separate module and needs
  `@AutoConfigureTestRestTemplate`. Old tutorials using either will not compile as-is.
- **Context caching:** tests with the same configuration share one started context, so
  a second `@SpringBootTest` class costs almost nothing.
- **Source:** [Spring Boot reference — Testing Spring Boot applications](https://docs.spring.io/spring-boot/reference/testing/spring-boot-applications.html)

   `HELP.md`). Run `verify` from the root again: the generated `InventoryApplicationTests`
   runs and passes.

### Slice 2 — the service reports itself healthy

1. **Red:** write `HealthEndpointTest` in `src/test/java/com/stadium/inventory/`: it starts
   the app on a random port and asserts that `GET /actuator/health` returns **200** with a

   That 404 is the right red; a compile error is not.
2. **Green:** add **Spring Boot Actuator** the just-in-time way — same settings on
   start.spring.io, add the dependency, **Explore**, copy only that dependency (and its

> **Trap:** name it `…Test`, not `…IT`. Surefire runs `*Test` classes; `*IT` classes need
> the Failsafe plugin, which isn't configured yet — an `IT` would silently never run.

### Slice 3 — port 8081 and the commands
